# FUNCTIONAL_SPEC.md

# 자취방 설명서 — 기능 명세서

## 1. 문서 개요

### 1.1 목적

본 문서는 자취방 설명서의 핵심 기능과 세부 동작 조건을 정의한다.

개발 과정에서 AI가 생성한 코드가 요구사항을 충족하는지 확인하기 위한 기준 문서로 활용한다.

### 1.2 서비스 목표

처음 자취하는 사용자가 집 안에서 관리해야 할 항목을 쉽게 발견하고 관리 일정을 설정하며 완료 기록을 남길 수 있도록 한다.

### 1.3 핵심 기능

| ID  | 기능           | 설명                                      |
| --- | -------------- | ----------------------------------------- |
| F01 | 관리 대상 등록 | 공간과 관리 항목을 등록하고 수정한다.     |
| F02 | 관리 주기 관리 | 관리 일정을 계산하고 우선순위를 표시한다. |
| F03 | 관리 히스토리  | 관리 완료 내역을 기록하고 관리한다.       |

# 2. F01 — 관리 대상 등록

## F01-01. 최초 이용 시 온보딩 진입

### 목적

처음 사용하는 사용자가 자신의 주거 환경에 맞는 관리 대상을 설정하도록 한다.

### 동작

1. 사용자가 서비스에 접속한다.
2. 온보딩 완료 여부를 확인한다.
3. 완료하지 않았다면 온보딩 페이지로 이동한다.
4. 완료했다면 홈으로 이동한다.

### 조건

- 온보딩 완료 여부는 localStorage에 저장한다.
- 저장 데이터 로딩이 끝나기 전에는 이동 여부를 판단하지 않는다.
- 온보딩 완료 사용자가 온보딩 URL로 접근하면 홈으로 이동한다.

### 예외

저장된 온보딩 데이터가 손상된 경우 오류를 처리하고 안전한 초기 상태를 제공한다.

---

## F01-02. 공간 선택

### 목적

사용자의 집에 존재하는 공간을 선택하도록 한다.

### 동작

1. 기본 공간 5개를 표시한다.
2. 사용자는 하나 이상의 공간을 선택한다.
3. 선택한 공간을 기준으로 다음 단계의 관리 항목을 표시한다.

### 기본 공간

- 주방
- 욕실
- 세탁 공간
- 생활 공간
- 현관

### 조건

- 여러 공간을 선택할 수 있다.
- 최소 하나의 공간을 선택해야 다음 단계로 진행할 수 있다.
- 사용자는 직접 공간을 추가할 수 있다.
- 직접 추가한 공간에는 고유 ID를 부여한다.

---

## F01-03. 공간별 기본 관리 항목 선택

### 목적

사용자가 평소 인지하지 못했던 관리 항목을 발견하도록 한다.

### 동작

1. 선택한 공간을 하나씩 표시한다.
2. 해당 공간의 기본 관리 항목을 표시한다.
3. 사용자는 실제 집에 존재하는 관리 항목을 선택한다.
4. 다음 공간으로 이동한다.
5. 모든 공간의 선택을 완료하면 주기 설정 단계로 이동한다.

### 조건

- 기본 관리 항목은 총 22개이다.
- 공간별로 관련 항목만 표시한다.
- 관리 항목은 여러 개 선택할 수 있다.
- 공간에 해당하는 항목이 없다면 건너뛸 수 있다.
- 온보딩 전체에서 최소 하나의 관리 항목을 등록해야 한다.

### 데이터 처리

기본 항목을 선택하면 해당 항목을 참조하는 사용자 Item을 생성한다.

예시:

```js
{
  id: "item-001",
  templateId: "living-ac-filter",
  spaceId: "living",
  name: "에어컨 필터 청소",
  intervalDays: 14
}
```

실제 저장 시에는 ARCHITECTURE.md에 정의된 나머지 필드도 포함한다.

### templateId 정책

- 기본 항목을 선택하면 DefaultItem.id를 templateId에 저장한다.
- 사용자 Item의 id는 별도로 생성한다.
- 기본 항목의 관리 설명과 출처는 templateId를 통해 조회한다.
- 사용자가 직접 만든 항목은 templateId를 null로 저장한다.

---

## F01-04. 관리 주기 및 기존 관리일 설정

### 목적

등록할 관리 항목의 초기 관리 정보를 설정하도록 한다.

### 동작

1. 선택한 관리 항목을 표시한다.
2. 기본 권장 주기가 있다면 초기값으로 제공한다.
3. 사용자는 주기를 수정할 수 있다.
4. 사용자는 마지막으로 관리한 날짜를 입력할 수 있다.
5. 설정 내용을 저장한다.

### 조건

- 관리 주기는 양의 정수 일수로 입력한다.
- 관리 주기를 입력하지 않아도 등록할 수 있다.
- 마지막 관리일은 선택 입력이다.
- 마지막 관리일은 오늘 또는 과거 날짜만 허용한다.
- 미래 날짜는 허용하지 않는다.

### 기본 주기와 사용자 주기

기본 콘텐츠:

```js
{
  recommendedIntervalDays: 14;
}
```

사용자 Item:

```js
{
  intervalDays: 30;
}
```

실제 일정 계산에는 사용자 Item의 intervalDays를 사용한다.

### 초기값 처리

- recommendedIntervalDays가 숫자이면 intervalDays의 초기값으로 복사한다.
- recommendedIntervalDays가 null이면 intervalDays도 null로 시작한다.
- 사용자는 초기값을 자유롭게 수정할 수 있다.
- 기본 권장 주기가 변경되어도 이미 저장된 사용자 주기는 자동으로 변경하지 않는다.

### 기존 관리일 처리

사용자가 마지막 관리일을 입력하면 다음 History를 생성한다.

```js
{
  id: "history-001",
  itemId: "item-001",
  managedAt: "2026-11-04",
  type: "initial",
  productUsed: "",
  memo: "",
  createdAt: "2026-11-04T09:00:00.000Z"
}
```

사용자가 날짜를 입력하지 않았다면 초기 History를 생성하지 않는다.

## F01-05. 온보딩 진행 상태 저장

### 목적

사용자가 온보딩 도중 페이지를 벗어나더라도 이어서 진행할 수 있도록 한다.

### 동작

1. 사용자가 공간이나 관리 항목을 선택한다.
2. 진행 상태를 자동 저장한다.
3. 사용자가 다시 접속하면 저장된 단계부터 이어서 진행한다.

### 조건

- 현재 단계
- 선택한 공간
- 선택한 관리 항목
- 입력 중인 주기 및 날짜

위 정보를 온보딩 draft에 저장한다.

온보딩을 완료하면 completed를 true로 변경한다.

---

## F01-06. 관리 대상 추가

### 목적

온보딩 이후에도 새로운 관리 항목을 추가할 수 있도록 한다.

### 동작

1. 관리 대상 목록에서 추가 버튼을 선택한다.
2. 등록할 공간을 선택한다.
3. 기본 관리 항목을 선택하거나 직접 입력한다.
4. 관리 주기와 추가 정보를 입력한다.
5. 저장한다.

### 조건

- 관리 항목 이름은 필수이다.
- 소속 공간은 필수이다.
- 관리 주기는 선택이다.
- 모델명, 규격, 이미지, 메모는 선택이다.
- 기본 항목을 선택한 경우 templateId를 저장한다.
- 직접 추가한 경우 templateId는 null이다.

### 예외

필수 입력값이 누락되면 저장하지 않고 오류 메시지를 표시한다.

---

## F01-07. 관리 대상 수정

### 목적

등록된 관리 항목의 정보를 변경할 수 있도록 한다.

### 수정 가능 정보

- 관리 항목 이름
- 소속 공간
- 관리 주기
- 모델명
- 규격
- 이미지
- 메모

### 조건

- 수정한 정보는 저장 후 즉시 화면에 반영한다.
- 관리 주기를 변경하면 다음 관리일을 다시 계산한다.
- 기존 History는 유지한다.
- 기본 권장 주기는 변경하지 않는다.

### 주의사항

기본 항목의 이름이나 소속 공간을 수정해도 templateId를 유지한다. 다른 관리 대상으로 변경하려면 사용자가 수정 화면에서 “직접 등록 항목으로 전환”을 명시적으로 선택하고 저장한다. 이때 templateId를 null로 해제하며 기존 History는 유지한다. 저장 전에는 원래 연결로 되돌릴 수 있다.

---

## F01-08. 관리 대상 삭제

### 목적

더 이상 관리하지 않는 항목을 삭제할 수 있도록 한다.

### 동작

1. 관리 대상 상세 페이지에서 삭제를 선택한다.
2. 확인 메시지를 표시한다.
3. 사용자가 확인하면 항목을 삭제한다.
4. 연결된 관리 기록도 삭제한다.
5. 관리 대상 목록으로 이동한다.

### 조건

- 삭제는 확인 후 실행한다.
- 삭제한 Item과 연결된 History를 모두 삭제한다.
- 다른 Item의 History는 영향을 받지 않는다.
- 삭제 후 목록과 대시보드를 갱신한다.

---

# 3. F02 — 관리 주기 관리

## F02-01. 기본 권장 주기 제공

### 목적

관리 경험이 부족한 사용자가 적절한 관리 주기를 설정하도록 돕는다.

### 동작

1. 사용자가 기본 관리 항목을 선택한다.
2. 기본 콘텐츠의 권장 주기를 조회한다.
3. 권장 주기가 있으면 초기값으로 표시한다.
4. 권장 주기의 출처 유형과 안내 문구를 표시한다.

### 조건

- 기본 권장 주기는 DefaultItem.recommendedIntervalDays를 사용한다.
- 출처 유형은 DefaultItem.intervalSourceType을 사용한다.
- 주기 미설정 항목은 직접 설정하도록 안내한다.
- 권장 주기는 제품과 사용 환경에 따라 달라질 수 있음을 안내한다.

### 출처 표시

- official: 제조사·기관 안내 기반
- suggested: 서비스 참고값
- null: 공통 주기 미설정

공식 안내 기반이라고 해서 모든 제품에 공통 적용되는 값으로 설명하지 않는다.

---

## F02-02. 사용자 관리 주기 설정

### 목적

사용자가 자신의 생활 환경에 맞는 관리 주기를 설정하도록 한다.

### 동작

1. 사용자가 관리 주기를 입력하거나 수정한다.
2. 입력값을 검증한다.
3. intervalDays에 저장한다.
4. 다음 관리일을 다시 계산한다.

### 조건

- 양의 정수만 허용한다.
- null을 허용한다.
- 0과 음수는 허용하지 않는다.
- 소수는 허용하지 않는다.
- 기본 권장 주기와 사용자 주기는 독립적으로 관리한다.

### 예시

기본 권장 주기: 14일

사용자 설정 주기: 30일

실제 계산 주기: 30일

---

## F02-03. 마지막 관리일 계산

### 목적

관리 기록을 기준으로 마지막 관리일을 정확하게 계산한다.

### 계산 규칙

해당 Item에 연결된 History 중 가장 최근 managedAt을 사용한다.

```text
lastManagedDate = MAX(History.managedAt)
```

### 조건

- initial 기록도 계산에 포함한다.
- completed 기록도 계산에 포함한다.
- 기록이 없으면 null이다.
- Item에는 lastManagedDate를 별도로 저장하지 않는다.

---

## F02-04. 다음 관리일 계산

### 목적

사용자가 다음 관리 시점을 확인하도록 한다.

### 계산 규칙

```text
nextDueDate = lastManagedDate + intervalDays
```

### 예시

마지막 관리일: 2026-11-04

관리 주기: 14일

다음 관리일: 2026-11-18

### 조건

- 마지막 관리일이 없으면 null이다.
- 관리 주기가 없으면 null이다.
- 날짜는 YYYY-MM-DD 형식으로 계산한다.
- 사용자 로컬 날짜를 기준으로 처리한다.
- Item에는 nextDueDate를 별도로 저장하지 않는다.

---

## F02-05. 관리 상태 판별

### 목적

관리 항목의 긴급도를 직관적으로 표시한다.

### 상태 정의

| 상태      | 조건                     |
| --------- | ------------------------ |
| 관리 지연 | 다음 관리일이 오늘 이전  |
| 오늘 관리 | 다음 관리일이 오늘       |
| 관리 임박 | 다음 관리일까지 1~7일    |
| 관리 예정 | 다음 관리일까지 8일 이상 |
| 미설정    | 다음 관리일 계산 불가    |

### 조건

- 현재 날짜를 기준으로 상태를 계산한다.
- 날짜가 바뀌면 상태가 달라질 수 있다.
- Item에는 status를 저장하지 않는다.

---

## F02-06. 홈 대시보드

### 목적

사용자가 우선적으로 관리해야 할 항목을 확인하도록 한다.

### 표시 정보

- 관리 항목 이름
- 소속 공간
- 다음 관리일
- 관리 상태
- 관리 완료 기능

### 정렬 기준

1. 관리 지연
2. 오늘 관리
3. 관리 임박
4. 관리 예정

미설정 항목은 별도 영역으로 표시한다.

### 조건

- 상태별 우선순위를 적용한다.
- 같은 상태에서는 다음 관리일이 빠른 순서로 정렬한다.
- 관리 기록이 추가되면 화면을 갱신한다.
- 관리 주기가 변경되면 화면을 갱신한다.

---

# 4. F03 — 관리 히스토리

## F03-01. 관리 완료 기록

### 목적

사용자가 실제로 수행한 관리 작업을 기록하도록 한다.

### 동작

1. 관리 항목에서 관리 완료 버튼을 선택한다.
2. 기록 작성 페이지로 이동한다.
3. 관리 날짜를 입력한다.
4. 선택 정보를 입력한다.
5. 저장한다.

### 입력 항목

| 항목                | 필수 여부 |
| ------------------- | --------- |
| 관리 날짜           | 필수      |
| 사용 제품 또는 부품 | 선택      |
| 메모                | 선택      |

### 조건

- 관리 날짜는 오늘 또는 과거 날짜만 허용한다.
- 미래 날짜는 허용하지 않는다.
- 저장된 기록의 type은 completed이다.
- 저장 후 관리 일정을 다시 계산한다.
- 중복 클릭으로 동일한 요청이 반복 저장되지 않도록 처리한다.

---

## F03-02. 관리 대상별 히스토리 조회

### 목적

특정 관리 항목의 관리 이력을 확인하도록 한다.

### 동작

1. 관리 대상 상세 페이지에 접근한다.
2. 해당 Item과 연결된 History를 조회한다.
3. 관리 날짜를 기준으로 최신순 정렬한다.
4. 기록 목록을 표시한다.

### 표시 정보

- 관리 날짜
- 사용 제품 또는 부품
- 메모
- 기록 유형

### 조건

- 다른 관리 항목의 기록은 표시하지 않는다.
- 기록이 없다면 빈 상태 안내를 표시한다.

---

## F03-03. 전체 히스토리 조회

### 목적

사용자가 모든 관리 활동을 한곳에서 확인하도록 한다.

### 동작

1. 하단 내비게이션에서 히스토리를 선택한다.
2. 전체 History를 조회한다.
3. 관리 날짜를 기준으로 최신순 정렬한다.
4. 각 기록의 관리 항목 이름과 관리 내용을 표시한다.

### 조건

- 실제 관리 날짜인 managedAt을 정렬 기준으로 사용한다.
- createdAt을 관리 날짜 대신 사용하지 않는다.
- 동일 날짜의 기록은 createdAt을 보조 정렬 기준으로 사용할 수 있다.

---

## F03-04. 관리 기록 수정

### 목적

잘못 입력한 관리 기록을 수정할 수 있도록 한다.

### 동작

1. 히스토리에서 수정할 기록을 선택한다.
2. 별도의 수정 페이지로 이동한다.
3. 관리 날짜, 사용 제품, 메모를 수정한다.
4. 저장한다.

### 조건

- 관리 날짜는 필수이다.
- 미래 날짜는 허용하지 않는다.
- 관리 날짜를 변경하면 마지막 관리일과 다음 관리일을 다시 계산한다.
- 메모 또는 사용 제품만 변경하면 일정 계산 결과는 유지된다.
- 수정 후 기록 목록과 상세 화면을 갱신한다.

---

## F03-05. 관리 기록 삭제

### 목적

잘못 등록한 관리 기록을 삭제할 수 있도록 한다.

### 동작

1. 삭제할 기록을 선택한다.
2. 삭제 확인 메시지를 표시한다.
3. 사용자가 확인하면 삭제한다.
4. 남은 기록을 기준으로 관리 일정을 다시 계산한다.

### 조건

- 최신 기록이 삭제되면 남은 기록 중 가장 최근 날짜를 사용한다.
- 모든 기록이 삭제되면 마지막 관리일은 null이 된다.
- 마지막 관리일이 null이면 다음 관리일도 null이 된다.
- 다른 관리 항목의 기록은 영향을 받지 않는다.

---

## F03-06. 관리 기록 중복 및 정렬 처리

### 목적

같은 날짜에 여러 작업을 수행한 경우에도 정확한 기록을 유지한다.

### 조건

- 동일한 Item에 같은 날짜의 기록을 여러 개 등록할 수 있다.
- 각 기록은 고유한 ID를 가진다.
- 동일 날짜의 기록이 여러 개여도 마지막 관리일은 해당 날짜로 계산한다.
- 관리 날짜가 같으면 생성 시각을 보조 정렬 기준으로 사용할 수 있다.
- 의도하지 않은 중복 제출은 방지한다.

---

# 5. 공통 기능

## C01. 데이터 영속성

### 목적

새로고침 이후에도 사용자 데이터를 유지한다.

### 조건

- 사용자 데이터는 localStorage에 저장한다.
- 데이터 저장과 조회는 Repository 계층에서 처리한다.
- 컴포넌트에서 localStorage에 직접 접근하지 않는다.
- 저장에 실패하면 사용자에게 오류를 안내한다.
- 저장 실패를 성공으로 처리하지 않는다.

---

## C02. 입력값 검증

### 검증 대상

- 관리 항목 이름
- 공간 선택
- 관리 주기
- 관리 날짜
- 관리 기록

### 조건

- 필수값이 없으면 저장하지 않는다.
- 관리 주기는 null 또는 양의 정수이다.
- 관리 날짜는 유효한 YYYY-MM-DD 형식이다.
- 미래 관리 날짜는 허용하지 않는다.
- 존재하지 않는 Item에 History를 연결하지 않는다.
- 존재하지 않는 Space에 Item을 연결하지 않는다.

---

## C03. 반응형 UI 및 내비게이션

### 목적

스마트폰에서 주요 기능을 편리하게 사용할 수 있도록 한다.

### 조건

- 모바일 화면을 우선 설계한다.
- 하단 내비게이션은 홈, 관리 대상, 히스토리로 구성한다.
- 작은 화면에서도 입력 폼과 버튼을 사용할 수 있어야 한다.
- 관리 대상 수정과 관리 기록 수정은 별도 페이지에서 진행한다.
- 잘못된 URL에는 404 안내를 표시한다.

# 6. 핵심 테스트 시나리오

## T01. 최초 온보딩 진입

**조건:** 온보딩 미완료

**예상 결과:** 서비스 접속 시 온보딩 페이지로 이동한다.

## T02. 온보딩 완료 후 홈 이동

**조건:** 공간과 관리 항목을 등록하고 온보딩을 완료한다.

**예상 결과:** 홈으로 이동하며 새로고침 후에도 완료 상태가 유지된다.

## T03. 기본 관리 항목 등록

**조건:** 에어컨 필터 청소를 선택한다.

**예상 결과:**

- 새로운 사용자 Item이 생성된다.
- templateId는 living-ac-filter이다.
- intervalDays의 초기값은 14이다.

## T04. 사용자 지정 관리 항목 등록

**조건:** 기본 콘텐츠에 없는 관리 항목을 추가한다.

**예상 결과:** templateId가 null인 Item이 생성된다.

## T05. 기본 권장 주기 변경

**조건:** 기본 권장 주기 14일을 사용자가 30일로 수정한다.

**예상 결과:**

- Item.intervalDays는 30이 된다.
- DefaultItem.recommendedIntervalDays는 14로 유지된다.
- 다음 관리일은 30일 기준으로 계산된다.

## T06. 관리 주기 미설정

**조건:** intervalDays가 null이다.

**예상 결과:** 다음 관리일과 관리 상태가 미설정으로 표시된다.

## T07. 마지막 관리일 미입력

**조건:** 관리 주기는 있으나 History가 없다.

**예상 결과:** 다음 관리일은 미설정이다.

## T08. 관리 완료 기록

**조건:** 2026-11-04에 관리 완료를 기록하고 관리 주기는 14일이다.

**예상 결과:** 다음 관리일은 2026-11-18이다.

## T09. 관리 지연 판별

**조건:** 다음 관리일이 오늘보다 이전이다.

**예상 결과:** 관리 지연 상태로 표시된다.

## T10. 관리 기록 수정

**조건:** 최신 관리 기록의 날짜를 수정한다.

**예상 결과:** 마지막 관리일과 다음 관리일이 수정된 날짜를 기준으로 계산된다.

## T11. 최신 기록 삭제

**조건:** 관리 기록이 2개 이상이고 최신 기록을 삭제한다.

**예상 결과:** 남은 기록 중 가장 최근 날짜가 마지막 관리일이 된다.

## T12. 모든 기록 삭제

**조건:** 특정 Item의 모든 History를 삭제한다.

**예상 결과:** 마지막 관리일과 다음 관리일이 미설정이 된다.

## T13. 관리 대상 삭제

**조건:** 관리 기록이 존재하는 Item을 삭제한다.

**예상 결과:** 해당 Item과 연결된 History가 삭제되고 다른 Item의 기록은 유지된다.

## T14. 새로고침 후 데이터 유지

**조건:** 관리 대상과 관리 기록을 등록한 뒤 새로고침한다.

**예상 결과:** 등록된 데이터가 유지된다.
