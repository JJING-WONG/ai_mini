# 관리 일정·상태 계산 (5단계)

## 동작

- 마지막 관리일: 해당 Item의 History에서 가장 최근 managedAt. initial/completed 모두 포함합니다.
- 다음 관리일: 마지막 관리일 + 사용자 intervalDays. 둘 중 하나라도 없으면 미설정입니다.
- 지연: 다음 관리일이 오늘 이전 / 오늘: 동일 / 임박: 1~7일 / 예정: 8일 이상.
- 정렬: 지연 → 오늘 → 임박 → 예정 → 미설정. 같은 상태는 다음 날짜가 빠른 순, 날짜가 같으면 ID 순입니다.
- 원본 Item에는 마지막 관리일·다음 관리일·상태를 저장하지 않습니다. Context 원본을 Service에서 계산한 화면 값으로 표시합니다.

홈 요약과 항목, 관리 목록 및 공간 필터, 상세 화면과 기록 화면의 기존 상태 표시가 같은 계산 결과를 사용합니다.
주기 수정·기록 배열 변경·삭제가 발생하면 다시 계산합니다. 6단계에서 기록 저장·수정·삭제 UI를 연결했으며 변경 즉시 다시 계산합니다.
주기만 있거나 기록만 있는 항목도 미설정으로 표시하고, 주기 설정 또는 관리 완료 기록으로 안내합니다.

## 달력 날짜와 오늘

`utils/date.js`는 연·월·일과 윤년 규칙을 정수 일수로 계산합니다. 날짜 문자열을 UTC 시각으로 바꾸거나 24시간 밀리초를 더하지 않습니다.
지원 날짜는 0001-01-01~9999-12-31입니다. 큰 양의 정수 주기가 지원 범위를 넘으면 화면 중단 없이 주기를 줄이라는 안내를 표시합니다.
오늘은 브라우저의 로컬 연·월·일에서 가져옵니다. 자정, 포커스 복귀, 화면 표시 상태 변경 및 주기적인 시계 확인 시 상태를 갱신합니다.
개발용 디자인 예시의 고정 날짜와 실제 사용자 일정은 분리합니다.

## 검증

`npm test`는 Vitest로 기존 저장소·온보딩·항목 테스트와 날짜·관리 일정 테스트를 모두 실행합니다.
윤년(1900/2000 포함), 월말·연말, 날짜 범위, 상태 0/1/7/8일 경계, 기록 변경, 정렬 및 원본 불변성을 확인합니다.
UTC, Asia/Seoul, America/Los_Angeles, Pacific/Apia에서 같은 계산 결과와 날짜 유효성 결과를 검증합니다.
서버 렌더링으로 홈·목록 정렬, 상세 상태, 실제 날짜 표시, 주기 수정·기록 제거·오늘 변경 시 갱신을 확인했습니다.
실제 브라우저 클릭·새로고침·자정 타이머·모바일 배치는 연결 오류로 아직 확인하지 못했습니다.

Vitest 설치 시 npm audit에서 기존 ESLint/minimatch 개발 도구 계열의 moderate 4건을 확인했습니다. 강제 버전 변경은 적용하지 않았습니다.
